# tla-go

A Go implementation of the TLA+ language and Java [TLC model checker](https://github.com/tlaplus/tlaplus), informed by [tla-ts](https://github.com/aidenybai/tla-ts).

**Work in progress:** the parser, evaluator, and model checker support only part of TLA+. Some temporal formulas, many module instance forms, operators and action forms, and proof obligations remain unimplemented. Unsupported models return errors; tla-go is not yet a replacement for Java TLC, and its CLI output is not yet TLC-compatible.

## Build and run

Install [mise](https://mise.jdx.dev/), then run:

```sh
mise trust
mise install
mkdir -p dist
mise exec -- go build -o dist/tla-go ./cmd/tla-go
./dist/tla-go examples/Counter.tla
```

The example deliberately deadlocks after reaching 3 and exits with code 11. Its `.cfg` file is read from the same directory as the `.tla` file. Use `-config path/to/model.cfg` to choose a configuration, `-deadlock` to disable deadlock reporting, or `-seed integer` to set the random seed. `-version` prints the build version. Multiple specifications and quoted globs are supported; globbed modules without a matching configuration are skipped, and the first failure determines the exit code.

For liveness debugging, `-debug-liveness` writes JSON lines to standard error. Events describe the explored state graph, the successor order used for incremental checks, and the states and components examined by fairness checks. When a cycle is built from witnesses, `fair-cycle` reports its start and ordered witnesses. `leads-to-component` reports model-state indices for pending leads-to components. The option does not change the model-checking result. Go callers can receive the same lines through `checker.Options.OnDebug`.

The CLI loads external modules named in `EXTENDS` or `INSTANCE` from `.tla` files beside the root module. Go callers can provide a `checker.ModuleLoader` through `CheckWithLoader` or `CheckConfigWithLoader`; `CheckWithOptions` and `CheckModuleWithOptions` also accept an `OnPrint` callback. Transitive extensions, shared dependencies, `LOCAL` definitions, named and parameterized instances, instances inside `LET`, and selected nested instances are supported, including instances of nested modules inherited through `EXTENDS`. Selected operator constants can be substituted with operators or lambdas, and bound names are renamed to avoid capture. Parameterized instances may contain functions, including recursive functions. Some combinations of nested modules and instances remain unsupported, as do function actions with operator parameters. Scalar constant substitutions and selected instance arguments are checked for constant-level expressions; full TLC level checking is not yet implemented.

Selected subexpression references support numbered operands, labels, bound values, operator arguments and `LET` definitions, including references through supported imported modules. More complex combinations and diagnostic details are not yet fully compatible.

User-defined operator arguments are evaluated lazily, including under primes and `ENABLED`. Function-definition parameters and some operator-argument paths are still evaluated eagerly, and TLC's full caching behavior is not yet reproduced.

`VIEW` reduces state identity using a configured expression, including supported fairness and counterexample reconstruction. `SYMMETRY` supports finite permutations of model values, including combinations with `VIEW`, nested sets, functions, and supported liveness forms. Per-check string and model-value ordering is used for supported finite sets, records, and state exploration; the full TLC ordering across imported modules is not yet implemented.

The checker supports a subset of finite-state safety models using `INIT` and `NEXT`, or the common `SPECIFICATION Spec` form `Init /\ [][Next]_vars`, plus invariants, state and action constraints, simple constants, and selected quantified and parameterized actions. Function definitions and selected recursive functions use deferred evaluation. Operator parameters and lambda expressions are supported in state expressions and selected action calls; substitutions that could capture names return an error. `ENABLED` uses successor generation for supported action forms. Function sets, record sets, Cartesian products, powersets, and unions are supported where enumerable. `Nat`, `Int`, and `STRING` support membership, filtered sets, and selected non-enumerable set operations. `EXTENDS FiniteSets` provides `Cardinality` and `IsFiniteSet` for supported values. `EXTENDS Sequences` provides `Seq`, `Len`, `Append`, `Head`, `Tail`, `SubSeq`, `SelectSeq`, and concatenation for supported values. `EXTENDS Bags` provides finite bag construction, counting, union, difference, containment, mapping and sub-bag enumeration. `EXTENDS TLC` provides `:>`, `@@`, `ToString`, `TLCEval`, `Permutations`, `SortSeq`, `Assert`, `Print`, `PrintT`, and the universal set `Any` for supported values. It reports an error for unsupported options and model constructs. Initial state and successor generation, printed value formatting, error messages, and TLC exit codes are not fully compatible yet.

Within an instantiated definition's `ENABLED`, direct references and selected references through other operators preserve TLC's variable-substitution boundary. More complex combinations of nested instances and action expressions are not yet fully compatible.

`TLCGet` and `TLCSet` support numeric and named registers, `-D` properties, stopping and pausing, unnamed actions, current levels, search counters, statistics, configuration and revision records. `TLCGet("spec")` describes supported specifications, properties, module instances, and action parameters; some complex forms and other runtime values are not yet fully compatible. `EXTENDS TLCExt` provides `AssertEq`, `AssertError`, `TLCDefer`, `TLCNoOp`, `TLCModelValue`, `TLCGetOrDefault`, `TLCGetAndSet`, `Trace`, `CounterExample`, and `ToTrace` for supported models. `CounterExample` exposes violation traces to postconditions, including supported liveness loops. `ALIAS` can transform counterexample states using the next state, trace, and level, and reports alias evaluation failures in the affected state. `POSTCONDITION` is evaluated after the search, and `_POSSIBLE` tracks state and action witnesses and reports unwitnessed predicates. Go callers can supply `Options.OnPause`; the CLI waits for a line of input when paused.

`EXTENDS Json` provides `ToJson`, `ToJsonArray`, `ToJsonObject`, `JsonSerialize`, `JsonDeserialize`, and their newline-delimited variants. The CLI reads and writes paths relative to its working directory, creating parent directories when writing. Go callers can supply `Options.ReadFile` and `Options.WriteFile`; without callbacks, reads fail as missing files and writes have no effect, as in tla-ts. The unchanged upstream `JsonTests` and `JsonValues` fixtures are covered; some JSON parse diagnostics may differ.

`TLC!RandomElement` and `EXTENDS Randomization` support seeded random choices, including sampling large Cartesian products and function sets without enumerating the full set. The seed defaults to zero and Go callers can set `Options.Seed`. Worker choices use the current state's TLC fingerprint and model-value intern ranks. Like Java TLC, interval sampling rejects sizes greater than 2^31−1. Some constant-level caching cases remain unsupported.

General temporal properties can combine state predicates, `[]`, `<>`, negation, conjunction, disjunction, implication, bounded quantifiers, conditionals, selected local `LET` definitions and parameterized operators, weak and strong fairness, and supported recurrent action formulas. A tableau product is checked with weak and strong fairness assumptions. Recurrence checks associated with fairness, including selected `TLCGet` reads and fairness actions with effects, are evaluated during state exploration and reused in cycle checks. Lasso recovery replays supported `Init` and `Next` effects before naming violated properties. Checks involving effects, random choices, dynamic `TLCGet` keys or `TLCGet("duration")` are not yet fully aligned with Java TLC, and different lasso choices can change reported properties or output when runtime values change. General formulas with pure state predicates and no fairness assumptions also support `VIEW` and symmetry reductions that merge distinct successors. General formulas involving action predicates, fairness assumptions or effects can still return an error when such reductions merge successors; other temporal constructs remain unsupported.

For pure `P ~> Q` properties without state reductions, counterexample selection tracks the pending obligation separately from the model state and uses Java TLC's successor order, including selected weak-fairness cases. Other liveness forms can still select different counterexamples.

Selected evaluation failures, including division by zero, failed `Assert`, and invalid function applications, return status `error` with a `Failure` containing the message, trace, and TLC exit code. Unsupported constructs and other errors still return a Go error.

## Development

Run `mise run format`, `mise run lint`, `mise run test`, or `mise run ci`. Lint includes go vet, actionlint, and cccc, enforcing cognitive complexity at most 10 and cyclomatic complexity at most 8 for production functions. It also uses gosimilarity to reject functions of at least 12 lines whose normalized syntax matches exactly. Run `mise run similarity` to review candidates of at least 8 lines and 95% similarity; a match is a refactoring candidate, not proof that two functions behave identically. Both similarity commands use the tool's defaults, which exclude tests and generated files. `mise exec -- go test -bench=. -benchmem ./checker ./evaluator ./value` runs the current microbenchmarks. The workflow in `.github/workflows/release.yml` builds CGO-free binaries for Linux, macOS, and Windows on amd64 and arm64 when a `v*` tag is pushed, then publishes archives and SHA-256 checksums to a GitHub release.

CI also runs secret scanning, CodeQL, govulncheck, OSV-Scanner, dependency review, zizmor, OpenSSF Scorecard, and parser fuzzing. Dependabot updates Go modules and GitHub Actions. Run `mise run secrets`, `mise run security:dependencies`, and `mise run security:workflows` for the corresponding local checks. Native binary smoke tests run on Linux, macOS, and Windows.

CI also compares selected behavior directly with Java TLC 1.7.4, downloading the official release JAR and checking its SHA-256. To run these checks locally, set `TLC_JAR` to an absolute path to a TLC JAR and run `mise exec -- go test ./checker ./cmd/tla-go -run '^TestJavaTLC' -count=1`. The current Java comparison covers only a small part of TLC; the older tla-ts fixtures below are additional regression evidence, not proof of Java compatibility. Java TLC versions can differ in seeded random output.

The `OneBitMutexNoSymmetryMC.trace.json` fixture records the complete counterexample asserted by `OneBitMutexNoSymmetryTest` at the Java TLC 1.7.4 commit `5a47802b5c391f59ecdd44117981f4ff8c0656ba`; both implementations are checked against it.

Unchanged `RandomSubset`, `RandomSubsetNext`, `RandomSubsetSetOfFcns`, `RandomElement`, and `RandomElementXandY` models from that commit are checked against Java JUnit expectations and direct Java executions for state counts and counterexamples. TLC coverage assertions are not yet implemented.

For representable set sizes, `RandomSubset` uses TLC 1.7.4's enumeration by default, including its repeated picks at the maximum interval size. `-modern-random-subsets` selects the newer enumeration used by the 2026-10-28 TLC development build; Go callers can set `Options.ModernRandomSubsets`. Other seeded random behavior is not yet fully compatible across TLC versions.

The existing tla-ts-derived fixture corpus is pinned to commit `19c763f07fda4b098e8a24405301628a424547c0`; Java TLC is the compatibility target. The lexer is tested against token snapshots for all 139 TLA+ fixtures at that commit. The partial parser is tested against selected examples and projections of 132 upstream fixture ASTs; see `syntax/parser/testdata/README.md` for the projection limits and excluded cases. The evaluator compares 180 general expressions and 32 bag expressions against upstream results. The checker compares 100 cases, including the complete upstream Mutex model and the Semantics, Assignments, Queue, and Unicode fingerprint fixtures. It also checks the unchanged upstream `BagsTest`, `test36`, and `test50` fixtures, five bag state-space models, selected printing cases including multiline and non-enumerable function output, the upstream `Any` cases, original TLC runtime and level fixtures, and `_POSSIBLE` cases, plus 71 module cases and 99 temporal cases, plus generated fairness, guarded-safety, ordered-eventuality, multi-stage ordered-eventuality, recurrence-implication, and pretty-print cases. Supported temporal forms include `[]P`, `[][A]_v`, `[](P => []Q)`, `<>P`, `[]<>P`, `<>[]P`, `<>(P /\ <>Q)`, `[]<>P => []<>Q`, `<>[]P \/ []<>Q`, `P ~> Q`, `P ~> []Q`, and `[]<><<A>>_v`, with weak and strong fairness and bounded universal quantifiers over constant sets. In recurrence implications and stability disjunctions, recurrence can also be an action such as `[]<><<A>>_v`; state and action recurrence assumptions are supported in specifications. P and Q must otherwise be state predicates, and fairness subscripts must cover all variables. Finite recursive operators that expand to ordered eventualities are supported when their recursion and conditions can be resolved from constants. Neither component implements every value or expression type. The source and tests derived from tla-ts, including `examples/Counter.*`, are covered by [UPSTREAM-LICENSE](UPSTREAM-LICENSE).

For models containing wide Unicode string literals, the checker uses TLC FP64 when no model values are configured, so it can reproduce TLC string fingerprint collisions. Model-value interning and TLC variable and string ordering are not yet fully implemented; models that include configured model values or call `TLCModelValue` currently use exact state keys instead.
